<Section title="Variants">

`appearance` sets how much attention the link draws: `default` is outlined, `primary` has the brand
fill, and `subtle` has no border and no fill until hover. `tone` changes only `primary`: `warning`
and `error` give it their own fill. Any other pairing, including `brand`, renders the appearance's
own look, so `tone="warning"` on a default link button changes nothing.

Link Button still takes the older `appearance` prop, where Button now takes `prominence` and `tone`;
the change is part of the pending Button-family revision.

<Example of={LinkButtonStories.Variants} />

<Subsection title="Sizes">

Four control heights, from `xs` (24px) to `lg` (48px), the same as Button so the two line up in a
row. `lg` also sets the label one type size larger. Icons are the same size at every link button
size, and there's no prop to change them.

<Example of={LinkButtonStories.Sizes} />

</Subsection>

<Subsection title="On dark surfaces">

Set `isInverse` on a link button that sits on a dark or bold surface, such as a Banner. It drops the
fill and border, uses the inverse text color, and swaps the dark hover and press overlays for light
ones. One inverse look serves every appearance. `isDisabled` flattens it the same way it flattens
`tone`.

<Example of={LinkButtonStories.Inverse} />

</Subsection>

</Section>

<Section title="Behavior">

<Subsection title="Loading">

`isLoading` shows a Spinner centered over the content and ignores clicks, so the link doesn't
navigate. The link button keeps its exact size: the label and icons stay in place, hidden, so
nothing around it shifts. The label stays the accessible name, `aria-busy` tells assistive
technology it's busy, and the link stays in the tab order.

<Example of={LinkButtonStories.Content} caption="Icon placement, loading, internal, in-page, and external targets, and a row in a card." />

</Subsection>

<Subsection title="Disabled">

Anchors have no `disabled` attribute, so `isDisabled` removes the `href`, sets
`aria-disabled="true"`, and takes the link out of the tab order. With no `href`, nothing can open it:
not a click, a middle click, or the browser's context menu. A loading link button works the same
way, except that it stays focusable.

</Subsection>

<Subsection title="Opening in a new tab">

With `target="_blank"`, Link Button adds hidden text after the label, "(opens in a new tab)" (set it
with `newTabLabel`), and, with no `rel`, adds `rel="noopener noreferrer"`. A `rel` you pass replaces
that default rather than adding to it, so pass one only when you need something else.

</Subsection>

<Subsection title="Focus and hover">

Keyboard focus shows the hover fill together with the shared Focus Ring, so a keyboard user sees both
signals at once.

</Subsection>

<Section title="Accessibility">

- Link Button renders a native `a` with an `href`, so it's announced as a link, can be opened in a
  new tab, and shows where it goes. Don't give it `role="button"`.
- The visible label is the accessible name. Name the destination ("View invoice", not "Click
  here"). The icons are hidden from assistive technology.
- `isDisabled` removes the `href` and sets `aria-disabled="true"` and `tabindex="-1"`, so the link
  leaves the tab order and assistive technology reports it as unavailable.
- A loading link button stays focusable, with `aria-busy` and `aria-disabled`, and its label stays
  its accessible name.
- With `target="_blank"`, the accessible name ends with "(opens in a new tab)", in hidden text, as on
  Link.

<Keyboard>
  <Key keys="Tab">Moves focus to the link button. A disabled one is skipped.</Key>
  <Key keys="Enter">Follows the link, unless it's disabled or loading.</Key>
  <Key keys="Space">Scrolls the page, as on any link. It doesn't activate Link Button.</Key>
</Keyboard>
