# Radio

Radio lets a user select exactly one option from a mutually exclusive set. It's almost always used
inside `RadioGroup`, which owns the shared `name`, single-selection value, and accessible group
labelling - a standalone `Radio` outside a group has nothing to be mutually exclusive with.

<Canvas of={RadioStories.Playground} />

## When to use

- Selecting one option from a short, fully-visible set of mutually exclusive choices.
- Form questions with a single correct answer.
- Settings and preferences where only one choice applies.

## When not to use

- **When more than one option can be selected.** Use `Checkbox`.
- **When the list is long enough to need scrolling or search.** Consider a Select or Combobox.
- **When the choice is a single, immediate on/off setting** rather than one of several named
  options. Use `Switch`.

## Anatomy

<Canvas of={RadioStories.Content} />

This component has two exports - `Radio` and `RadioGroup` - each with its own anatomy.

### Radio

1. **Root** - a `label` wrapping the whole control, so clicking the label text toggles the input.
2. **Input** - the native `input[type="radio"]`, visually hidden but present and focusable.
3. **Indicator** - decorative unchecked/checked icons, swapped by CSS off `:checked`.
4. **Label text** - optional. When absent, `aria-label` or `aria-labelledby` is required.

### RadioGroup

1. **Root** - a native `fieldset`.
2. **Legend** - the group's accessible name, when `label` is provided.
3. **Description** - optional helper text under the legend.
4. **Options** - `Radio` instances, either generated from the `options` prop or passed as `children`.
5. **Error message** - optional, connected to the fieldset with `aria-describedby` when `invalid`.

## Usage guidance

### Almost always inside RadioGroup

Radio only manages its own checked value - single-selection behavior (one shared `name`, mutual
exclusivity, group labelling) is `RadioGroup`'s job. Use the `options` API for a straightforward
list it renders for you, or `children` when the layout needs to be more custom - see Content for
both.

### Controlled and uncontrolled, at both levels

`Radio` takes `checked`/`defaultChecked`; `RadioGroup` takes `value`/`defaultValue`. Pick one pair
per group and stay consistent - `RadioGroup` decides whether it's controlled based on whether
`value` is passed, and threads the right prop down to each generated `Radio`.

### Orientation

`RadioGroup`'s `orientation` defaults to `vertical` with no gap between options. `horizontal` lays
options out in a row that wraps via `flex-wrap` once the container runs out of room, rather than
overflowing - see Edge Cases.

### Labelling

A visible `label` is the default and preferred path for both `Radio` and `RadioGroup`. Omit it only
in a dense context - a table row, a compact toolbar - where an adjacent visible label already
exists, and supply `aria-label` or `aria-labelledby` instead. Radio has no dev-time warning for a
missing accessible name today, so this is easy to get wrong silently - see Edge Cases.

### Invalid state

`invalid` sets `aria-invalid` on the input (or the fieldset, for `RadioGroup`) and switches the
hover/press treatment, but color alone doesn't carry the meaning - pair it with a visible message
via `errorMessage` (on `RadioGroup`) or `aria-describedby` (on a standalone `Radio`).

### Verifying interaction states

Radio predates the shared `data-force-state` convention that Checkbox, Button, and Avatar use -
its own CSS pins hover, press, and focus with `previewHover` / `previewPress` / `previewFocus`
classes instead. See States for both the pinned reference states and a live, click-driven example.

## Do / Don't

**Do** use `RadioGroup`'s `options` API for a straightforward list.

```tsx
<RadioGroup
  label="Preferred contact method"
  name="contact-method"
  options={[{ value: 'email', label: 'Email' }, { value: 'phone', label: 'Phone' }]}
  onValueChange={setValue}
/>
```

**Don't** hand-wire a shared `name` and selection state across standalone `Radio` instances when
`options` already does it.

```tsx
<Radio name="contact-method" value="email" label="Email" checked={value === 'email'} onCheckedChange={() => setValue('email')} />
<Radio name="contact-method" value="phone" label="Phone" checked={value === 'phone'} onCheckedChange={() => setValue('phone')} />
```

---

**Do** give a `RadioGroup` an accessible group name via `label`.

```tsx
<RadioGroup label="Preferred contact method" name="contact-method" options={options} />
```

**Don't** omit both `label` and an `aria-label`/`aria-labelledby` override - the group becomes
unnamed for assistive technology.

```tsx
<RadioGroup name="contact-method" options={options} />
```

---

**Do** pair `invalid` on `RadioGroup` with a visible `errorMessage`.

```tsx
<RadioGroup label="Preferred contact method" invalid errorMessage="Choose one option before continuing." options={options} />
```

**Don't** rely on the invalid color alone to communicate the problem.

```tsx
<RadioGroup label="Preferred contact method" invalid options={options} />
```
