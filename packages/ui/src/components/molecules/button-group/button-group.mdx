  only: each button keeps its own look, focus, and keyboard behavior.

<Section title="When to use">

<Usage>
<UseFor>

- A dialog's or a form's actions, such as Save and Cancel.
- A toolbar of related actions, such as Edit and Delete on a row.
- Stacked actions in a narrow space, with `orientation="vertical"`.
- Laying out Toggle Buttons that sit together, such as a set of filters.

</UseFor>
<UseInstead>

- **A main action with a few related alternatives:** <DocLink to="Components/Actions/Split Button" />, which joins the two into one shape.
- **More actions than fit in a row:** <DocLink to="Components/Actions/Dropdown Menu" />, opened from a Button or an Icon Button. Button Group doesn't wrap.
- **One action:** <DocLink to="Components/Actions/Button" /> on its own. A group of one adds nothing.
- **Choosing between options, such as a list or grid view:** <DocLink to="Components/Actions/Toggle Button" /> in the group, with the chosen value in your state. Button Group holds no selection.

</UseInstead>
</Usage>

</Section>

<Section title="Variants">

<Subsection title="Orientation">

`horizontal`, the default, lays the buttons out in a row; `vertical` stacks them in a column. Both
use the same 8px gap, and neither wraps, so use `vertical` where a row won't fit. The group is only
as wide as its buttons. In a vertical group, give each button `isFullWidth` to make them all as wide
as the widest one.

<Example of={ButtonGroupStories.Variants} caption="Horizontal and vertical, with two, three, and four buttons." />

</Subsection>

</Section>

<Section title="Behavior">

<Subsection title="Layout only">

Button Group doesn't pass anything to its buttons. Set `size`, `prominence`, and `tone` on each
button; the group never changes them. Buttons line up along their top edge rather than stretching,
so buttons of different sizes look uneven side by side.

</Subsection>

<Subsection title="Naming the group">

Give the group an `aria-label`, or point `aria-labelledby` at visible text, when nothing nearby says
what its buttons are for, such as a toolbar of icon-only actions. A name also gives the group
`role="group"`, so screen readers announce the name when focus enters it. Without a name, the group
is a plain `div` with no role. A `role` you pass, such as `toolbar`, replaces either.

<Example of={ButtonGroupStories.Composition} caption="A dialog's actions, a toolbar of Icon Buttons, and stacked full-width form actions." />

</Subsection>

</Section>

<Section title="Accessibility">

- Button Group renders a `div`. Without a name it has no role, and assistive technology reads its
  buttons as if they weren't wrapped.
- An `aria-label` or `aria-labelledby` adds `role="group"`, so the name is announced when focus
  enters the group. A `role` you pass wins over it, named or not, such as `toolbar`; a toolbar is
  one tab stop with arrow keys between its controls, which you then add yourself.
- The group is never a focus stop. Each button stays in the tab order on its own, in the order you
  pass them, and there's no arrow-key movement between them, because they're separate actions, not
  one control.

Button Group adds no keys of its own. Tab moves through its buttons in order, and each button
handles its own Enter and Space.

</Section>
