<Section title="When to use">

<Usage>
<UseFor>

- A form control that needs a visible label.
- Helper text under a control, such as a format or a limit.
- An error or success message about one control.
- Marking a control as required.

</UseFor>
<UseInstead>

- **A group of radios or checkboxes:** the groups on <DocLink to="Components/Forms/Radio" /> and <DocLink to="Components/Forms/Checkbox" />, which label the set with a legend. A label names one control.
- **A message about a whole section or page:** <DocLink to="Components/Feedback/Section Message" /> or <DocLink to="Components/Feedback/Inline Message" />.
- **A control with no visible label, such as a search box in a toolbar:** the control on its own, with an `aria-label`.
- **Several fields with a heading and actions:** <DocLink to="Components/Forms/Form" />, which lays out Fields in sections and rows.

</UseInstead>
</Usage>

<Section title="Variants">

<Subsection title="States">

`state` is `default`, `error`, or `success`. `default` shows the message as quiet helper text.
`error` and `success` color the message and put a status icon before it, and `error` also sets
`aria-invalid` on the control. `state` doesn't change the control's border: pass the control's own
`invalid` too, so the border and the message agree. `valid`, the earlier name for `success`, is
still accepted and looks the same.

<Example of={FieldStories.States} />

</Subsection>

<Subsection title="Context and size">

`context` is where the field sits, as for the controls it wraps. `default` keeps the label and
message flush with the control's edge, at every size. `inline` lines them up with the text inside
the control and passes `context="inline"` to the control, so the whole field reads as one inline
unit; a control that sets its own `context`, or a deprecated `appearance` or `tone`, keeps it.

`size` matters only for `inline`: it sets how far the label and message step in, 8px for `sm` and
`md` and 12px for `lg`, to match the control's own padding. It doesn't resize the control, so set
the same `size` on both. Inline is for controls with text inside, such as Text Field, Text Area, and
Select; it does nothing useful for a checkbox, radio, or switch.

<Example of={FieldStories.Contexts} caption="Context: default is flush at every size; inline steps the label and message in to the control's text and makes the control inline." />

</Subsection>

</Section>

<Section title="Behavior">

<Subsection title="What Field wires up">

Field clones its one child and fills in the props the child left unset: an `id` for the label to
point at, `aria-labelledby` naming the label (so a control that isn't a native input is named too),
`aria-describedby` for the message, `aria-invalid` for the error state, and `required`.
The control's own props always win, so its `id`, `aria-invalid`, and `required` are never
overwritten, and an `aria-describedby` it already has keeps its place, with the message added after
it. Because Field clones its child, `children` must be one element, not text, a fragment, or
several elements.

Every form control in the system passes them on: Text Field, Text Area, Select, Date Picker, Time
Picker, and Slider to their input; Rich Text Area to its editor; Date Time Picker names its group and
marks both inputs; Slider Range names its group, points the label at its lower handle, and gives
both handles the message, the error, and `required`.

<Example of={FieldStories.AnyControl} caption="The same label, message, and state on a Text Field, a Text Area, and a Slider." />

</Subsection>

<Subsection title="Required">

`required` shows a `*` after the label and passes the native `required` to the control. The `*` is
hidden from assistive technology, because the control's `required` already says it.

<Example of={FieldStories.Content} caption="Content: a required field, a field with helper text, and a field with no message." />

</Subsection>

<Subsection title="When errors show">

Field doesn't validate: set `state`, `message`, and the control's `invalid` from your own check.
When you show the errors follows one rule across the system:

1. **Check when the form is submitted**, not while someone is still typing their first answer.
2. **Show every error at once**: each field's own error, and a summary at the top of the form: a
   Section Message whose `errors` link to each field that needs fixing.
3. **Then update each field's error as its value changes**, so it clears as soon as it's fixed. The
   summary changes only on the next submit.

<Example of={FieldStories.EdgeCases} caption="Edge cases: validation by the rule (submit as it is, then fix each field), a long label and message in a narrow field, and a dark surface." />

</Subsection>

</Section>

<Section title="Accessibility">

- Field renders a `div` with a native `label` above the control and a message `div` below it. It has
  no role or focus stop of its own, and clicking the label focuses the control.
- The label's `htmlFor` points at the control's `id`: the control's own, else `controlId`, else one
  Field generates. The control also gets `aria-labelledby` naming the label, unless it has its own
  `aria-label` or `aria-labelledby`, in which case that name wins.
- The message's id is added to the control's `aria-describedby`, after any description the control
  already has, so it's read when the control gets focus.
- `state="error"` sets `aria-invalid` on the control unless the control sets its own. The status icon
  is hidden from assistive technology, so the message text has to carry the meaning.
- Errors show on submit, all at once, so a screen reader user isn't interrupted while typing. Move
  focus to the form's summary after a failed submit. Each link in the summary's `errors` moves focus
  to its field, which then reads its label and its error.
- `required` passes the native `required` to the control, and the `*` is hidden, so the requirement
  is announced once.
- Every form control in the system passes this wiring to its native element, including Rich Text
  Area's editor, which a `label` alone can't name.
- Wrap one control. A label names one control, so a group of radios or checkboxes needs Radio Group
  or Checkbox Group, which use a fieldset and a legend.

Field adds no keys of its own; focus goes straight to the control.

</Section>
