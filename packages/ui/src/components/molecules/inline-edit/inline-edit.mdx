export function LiveValue({ label, initial, context = 'inline' }) {
  const [value, setValue] = React.useState(initial);
  return (
    <InlineEdit value={value} onConfirm={setValue}>
      <TextField context={context} aria-label={label} />
    </InlineEdit>
  );
}

export function LivePair({ label, initial }) {
  const [value, setValue] = React.useState(initial);
  // A Key Value Pair is a `dt` and `dd`, so it sits in a Key Value List (a `dl`), even on its own.
  return (
    <KeyValueList>
      <KeyValuePair label={label} underline>
        <InlineEdit value={value} onConfirm={setValue} actionPlacement="end">
          <TextField context="inline" aria-label={label} />
        </InlineEdit>
      </KeyValuePair>
    </KeyValueList>
  );
}

<Section title="Variants">

<Subsection title="Action placement">

The cancel and confirm buttons float over the page rather than taking space, so the field keeps its
width while editing. `actionPlacement="below"`, the default, puts them 8px under the field, lined up
with its trailing edge. `actionPlacement="end"` puts them 8px past the field's trailing edge,
centered on it; use it in a row such as a Key Value Pair, and leave room beside the field. With
`end`, `actionAlignment="start"` keeps the buttons level with the first line of a Text Area that
grows, instead of centered on it.

`actionButtons={false}` hides the buttons. Enter and Escape still confirm and cancel.

<Example of={InlineEditStories.Variants} caption="With and without the action buttons: click or tab into either field to edit it." />

</Subsection>

</Section>

<Section title="Behavior">

<Subsection title="Starting an edit">

Inline Edit has no editing prop: editing always starts when the child gets focus, from a click or
from Tab. Until then, the child is read-only and shows `value`. It's the same element in both
states, so focus stays put when editing starts. When the read-only field already has focus, after
an edit ends, a click or Enter starts editing again.

<Example of={InlineEditStories.Content} caption="A live field, the sm and md sizes, and custom action labels." />

</Subsection>

<Subsection title="Confirming and cancelling">

Confirm, or Enter in a Text Field, calls `onConfirm` with the draft. In a Text Area, Enter adds a
line, and Ctrl+Enter or Cmd+Enter confirms. Cancel, or Escape, calls `onCancel` and shows `value`
again. Either way the field goes back to read-only and keeps focus, so someone using a keyboard
stays where they were: after Enter or Escape it never left, and after the cancel or confirm button
it moves back to the field, since the buttons go away.

Inline Edit doesn't change `value` itself. Set it in `onConfirm`; if you don't, the field shows the
old value again after confirming.

</Subsection>

<Subsection title="Leaving the field saves">

While editing, moving focus anywhere outside Inline Edit, by a click or by Tab, confirms the draft,
the same as the confirm button, unless `validate` rejects it. Moving to the cancel or confirm button doesn't. Only cancel or
Escape throws a draft away, so clicking elsewhere never loses an edit. If the draft is unchanged,
leaving just ends editing without calling `onConfirm`, so tabbing through the field and its buttons
doesn't report an edit that didn't happen. Enter or the confirm button still call `onConfirm` with
an unchanged value, since someone chose to confirm.

</Subsection>

<Subsection title="Checking the draft">

`validate` checks the draft whenever it would be confirmed: Enter, the confirm button, or focus
leaving. Return a message to reject the draft, or `undefined` to accept it. A rejected draft isn't
confirmed and isn't lost: the field stays in edit mode, the message shows under it in Field's error
look, and the field is marked invalid. After Enter or the confirm button, focus is in the field, so
people can fix it straight away. When focus left, Inline Edit doesn't pull it back: the draft and
its error wait in the field, with the buttons still showing.

After a rejected confirm, the message follows the draft as it changes, so it clears as soon as the
draft is fixed, the system's rule for when errors show. Escape and the cancel button still discard
the draft and the error. Inline Edit only checks: saving can still fail, so handle that in
`onConfirm`.

<Example of={InlineEditStories.Validation} caption="Change the docket number to 1482, then press Enter or click away: the error keeps the draft in the field." />

</Subsection>

<Subsection title="In a Field">

Field wires Inline Edit as it wires a Text Field. Inline Edit passes what Field gives it on to its
child, read-only and editing: the `id`, so clicking Field's label focuses the field; the label, as
`aria-labelledby`; the message, added to `aria-describedby`; Field's error, as `aria-invalid`;
`required`; and `context="inline"` when Field is inline. The child's own values win, as they do with
Field, so leave the child unnamed and without an `id` inside a Field.

`validate`'s message and Field's message both show: `validate`'s under the field while it rejects
the draft, and Field's below Inline Edit as always. They say different things: `validate`'s is about
the draft being edited, and Field's is help, or an error about the saved value, such as one from the
server. The field is described by both, Field's first, and stays invalid while either says so.
The buttons float over what's below the field, Field's message included, so in a Field use
`actionPlacement="end"` and leave room beside the field.

<Example of={InlineEditStories.InField} />

</Subsection>

<Subsection title="In a Table">

Inside a Table's editable cell, the read-only field shows an edit icon after the value, and a click
starts editing. While editing, the icon is removed, the cancel and confirm buttons sit inside the
cell at its trailing edge, and the field shows a line in the focus color along its bottom.

</Subsection>

field.

<Section title="Accessibility">

- Inline Edit renders a `div` with no role or name. The child keeps its own: name it with
  `aria-label`, or with the label of the Field or Key Value Pair around it. In a Field, Inline Edit
  passes Field's `id`, `aria-labelledby`, `aria-describedby`, `aria-invalid`, and `required` on to
  the child; the child's own values win.
- While read-only, the child has the native `readOnly` attribute, so it stays in the tab order and is
  announced as read-only. Focusing it starts editing and removes `readOnly`.
- The cancel and confirm buttons are Icon Buttons named by `cancelLabel` and `confirmLabel`, which
  also show as their tooltips. Write them for the value, such as "Save title", when "Confirm" alone
  isn't clear. Their Button Group has no name, so it adds no group role.
- After Enter, Escape, cancel, or confirm, focus is on the read-only field, so it isn't lost to the
  page. Enter or a click there starts editing again.
- When `validate` rejects the draft, the field gets `aria-invalid` and the message is added to its
  `aria-describedby`, after any description it already has, Field's message included. The message is in a polite live region,
  so it's read out after Enter, when focus doesn't move. Its status icon is hidden, so the text
  carries the meaning. Focus stays in the field after Enter or the confirm button.

<Keyboard>
  <Key keys="Tab">Moves into the field, which starts editing; then to cancel, then to confirm. Moving focus out of Inline Edit confirms a changed draft, and just ends editing when nothing changed.</Key>
  <Key keys="Enter">In a Text Field, confirms the draft, or shows the error and keeps editing when `validate` rejects it. On a focused cancel or confirm button, activates that button. On the read-only field, starts editing.</Key>
  <Key keys="Ctrl + Enter">In a Text Area, confirms the draft. Cmd + Enter does the same on a Mac.</Key>
  <Key keys="Escape">Cancels the edit and shows `value` again, with focus on the field.</Key>
</Keyboard>

</Section>

<Section title="API">

<PropsTable of={InlineEditStories} />

The child must accept `value`, `onChange`, `onFocus`, and `readOnly`, which Inline Edit sets on it;
Text Field and Text Area do. Inline Edit replaces the child's own `onChange` while editing and its
`onFocus` while read-only. While read-only it also wraps the child's `onClick` and `onKeyDown`: they
still run, then a click or Enter starts editing. While `validate` rejects the draft, Inline Edit also
sets `invalid` and `aria-invalid` on the child and adds the message to its `aria-describedby`. Its
own `id`, `aria-labelledby`, `aria-describedby`, `aria-invalid`, `required`, and `context`, which
Field sets, go on to the child in both modes, unless the child sets its own.

</Section>
