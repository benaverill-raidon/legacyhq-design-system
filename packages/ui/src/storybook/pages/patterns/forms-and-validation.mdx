<Section title="The problem">

Most work in LegacyHQ starts with a form: opening a matter, adding a client, scheduling a hearing.
Without one approach, the same answer is a Select on one screen and radios on the next, required
fields go unmarked, and a failed submit leaves people hunting for what's wrong.

Two questions settle most of it:

- **What kind of answer is it?** A line of text, one choice from a few, a date. The answer decides
  the control, and the control decides how it's labelled and how it shows an error.
- **What's wrong, and where?** An error belongs beside the control it's about, in words that say
  how to fix it. When a submit fails, a summary at the top says how many things need fixing and
  takes people to each one.

</Section>

<Subsection title="Laying out the form">

<DocLink to="Components/Forms/Form" /> lays out the controls and <DocLink to="Components/Forms/Field" /> labels each one.

- **Form** gives the header: `title`, `description`, and `requiredLegend`, the line "\* indicates a
  required field". Set it whenever a field is required.
- **FormSection** groups related fields under an optional title. Fields in a section stack one per
  line.
- **FormRow** puts short, related fields side by side, such as first and last name. It never stacks
  on a narrow screen, so keep long fields out of rows.
- **Field** puts the label above the control and the message below it. The message is helper text
  until there's an error. `required` shows the `*` and sets the control's native `required`.
- **FormFooter** holds the actions. The submitting Button needs `type="submit"`: Button defaults to
  `type="button"`.

</Subsection>

<Subsection title="Marking an error">

Field marks one control with `state`. `error` colors the message, adds a status icon, and sets
`aria-invalid` on the control; `success` confirms a check passed. Field doesn't change the control's
border, so pair `state="error"` with the control's own `invalid`. Radio Group and Checkbox Group take
`invalid` and `errorMessage` instead. The table is read from Field's TypeScript.

<Section title="Rules">

- **Choose the control by the answer.** A choice saved when the form is submitted is a Checkbox;
  a Switch takes effect right away, so it doesn't belong in a form with a submit button. A few
  options people should compare are radios, not a Select.
- **Label every control.** Field for one control, the legend of a Radio Group or Checkbox Group for
  a set. Mark required fields with `required` and set the form's `requiredLegend`.
- **Say what a field wants before anyone gets it wrong.** Helper text in Field's `message` gives the
  format, the limit, or who sees the value. Leave it out when the label says enough.
- **Check when people submit, then follow the value.** This is the system's rule for when errors
  show. Check on submit, not while people are still typing. Show every error at once, with the
  summary at the top. Then update each field's error as its value changes, so it clears as soon as
  it's fixed. Field doesn't validate and Form leaves the checks to you, so your code follows the
  rule: set `state`, `message`, and `invalid` from it.
- **Show a failed submit at the top and at each field.** Put a Section Message with
  `tone="error"` at the top of the form, naming each field that needs fixing and linking to it.
  Each field shows its own error. Don't show only one or the other. The summary is a live region, so
  change it on the next submit, not on every keystroke.
- **Write each error as what to do.** "Enter the client's first and last name", not "Invalid input."
- **Use your own check or the browser's, not both.** Form is a native `form`, so the browser checks
  `required` and stops the submit with its own message unless you set `noValidate`. Set it when you
  show the system's errors. Check a required Checkbox Group and a Rich Text Area yourself: the
  browser checks neither.
- **Show the submit is busy on its button.** Set `isLoading` on the submit Button while it saves. It
  keeps its size and label, and ignores clicks. Don't disable it or swap the label for "Saving…".
- **Confirm a save the way any message confirms.** A toast for a save that worked; a failure that
  needs fixing stays on the page. See <DocLink to="Patterns/Messages and Feedback" />.
- **Edit one value in place when it doesn't need a form.** Inline Edit has no error state, and
  leaving the field confirms the draft, so a value that needs a check that can fail belongs in a
  form, where Field can show the error.

</Section>

<Section title="Accessibility">

- Field's label names the control, its message is the control's description (`aria-describedby`),
  `state="error"` sets `aria-invalid`, and `required` sets the native `required`. The `*` is hidden,
  so the requirement is announced once.
- Radio Group and Checkbox Group are a `fieldset` named by the legend. Their `description` and
  `errorMessage` describe the fieldset and each option from `options`. A required Checkbox Group
  adds hidden text to the legend, such as "required", since checkboxes have no group requirement.
- No component moves focus when a submit fails. Move it to the summary yourself: Section Message
  takes a `ref` and `tabIndex={-1}`. It's a polite live region, but a message added with its content
  already in it may not be read out as it appears, so move focus to it rather than rely on that.
- Link each error in the summary to its field, and move focus to the field. The field then reads
  its label and its error.
- A loading Button sets `aria-busy`, and its label stays its accessible name.
- Form is a landmark only when it's named, and its title and section titles aren't headings. Pass
  `aria-label` or `aria-labelledby` if people should find it by landmark, and put the page's own
  heading above it.

</Section>
