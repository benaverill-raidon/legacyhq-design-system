<Section title="The problem">

Every screen waits for something: a matter's documents, a search, an upload, a save. Sometimes what
arrives is nothing: a new matter with no documents yet, or a search that matched no one. Without one
rule, the same wait is a skeleton on one screen and a spinner on the next, the page jumps when the
content lands, and an empty list looks the same as one that failed to load.

Three questions settle almost every case:

- **What do you know about what's coming?** Its shape, how much of it is left, or neither. The
  answer picks Skeleton, Progress Bar, or Spinner.
- **Did someone just ask for it?** The control they pressed shows that it's busy. Work they don't
  need to watch goes to a toast, so they can carry on.
- **When nothing comes, why?** Nothing has been added yet, nothing matched, or the load failed. Each
  says something different, and a failure is an error, not an empty state.

</Section>

<Section title="Rules">

- **Hold the layout when you know it.** Size skeletons like the content they stand in for, so
  nothing jumps when it arrives. When you don't know the shape, use a Spinner, not skeletons that
  guess.
- **Show the wait where the result will appear.** Skeletons stand where the content will be, a busy
  control where people pressed, a toast for work they don't need to watch. Show one of them for each
  wait, not two.
- **Mark the control that started it busy.** Set `isLoading` on the Button or Link Button: it keeps
  its size and its label, and ignores a second click. Don't swap the label for "Saving…", and don't
  also make it look disabled.
- **Only measured work gets a Progress Bar.** Set `value` from real progress, and put a count in
  `getValueText`. With no real number, use a Spinner: a made-up value misleads.
- **Background work goes in a toast that's replaced.** Start it with `toast.loading`, which stays
  until it's updated, then call `toast.success` or `toast.error` with the same `id`, so the result
  takes its place.
- **Say which kind of empty it is.** Nothing yet says what will appear and offers to add the first.
  No results names the search and offers to clear it. Never leave a bare "No data".
- **A load that failed is an error, not an empty state.** Show a Section Message with
  `tone="error"` in place of the content, with a way to try again. An Empty State would say there's
  simply nothing there.

</Section>

<Section title="Accessibility">

- Skeleton and Spinner are hidden from assistive technology unless they have a `label`. With one,
  they're a polite live region (`role="status"`) that reads it. Label one skeleton in a region, not
  each, and leave a Spinner unlabelled only beside visible text that says what's loading.
- Button and Link Button set `aria-busy` and `aria-disabled` while `isLoading`, and stay focusable,
  so focus doesn't jump while the action runs. The label stays the accessible name. Switch and Icon
  Button set `aria-busy` too.
- Table sets `aria-busy` while `loading`. Its skeleton rows are hidden from assistive technology.
- Progress Bar has `role="progressbar"`, named by `label`, with its value read as a percentage or as
  `getValueText`. It isn't a live region, so changes aren't announced on their own. Show the count
  beside it for sighted people.
- A loading toast is announced through Toast Group's polite live region. Loading reads no status
  word before the title, so the title has to say what's running.
- Empty State isn't a live region, and Table doesn't announce its rows running out. When a search
  empties the results, announce it from a region that stays on the page, such as a status message
  with the result count.
- Section Message is a polite live region by default, so a failure that appears in place of the
  content is read out.
- With reduced motion, Skeleton stops pulsing, Spinner stops turning, and Progress Bar's fill
  changes at once. The shapes stay, so the state is still shown.

</Section>
