<Section title="The problem">

Every screen has something to report: a save that worked, a document missing a signature, a filing
deadline, an outage. Without one rule, the same news arrives as a banner on one screen and a dialog
on the next, and the look of a message stops telling people how much it matters.

Two questions settle almost every case:

- **What is the message about?** The whole page, one section, one item, or one form control. The
  answer decides where it shows.
- **Can it pass, does it have to stay, or does it need an answer?** A confirmation can go away on
  its own. A problem someone has to fix stays until it's fixed. A decision stops the page until
  it's made.

</Section>

<Subsection title="Tone is a separate choice">

Each of them takes a `tone`: what the message means, named the same in every component. Not every
component takes every tone. Banner is for what affects everyone, so it has warning and error but no
success; confirm something that worked with a toast. The table is read from each component's
TypeScript.

<ToneMatrix components={['banner', 'section-message', 'inline-message', 'toast', 'modal-dialog']} />

- **`information`:** something useful to know. Nothing is wrong.
- **`success`:** something worked.
- **`warning`:** something will go wrong, or needs attention, if nothing changes.
- **`error`:** something went wrong, or is blocking. People have to act.
- **`default`:** no status, a neutral message.
- **`loading`:** Toast only, for work that's still running.

<Section title="Rules">

- **One message per event.** Show it once, in the place that matches its scope. Don't confirm a
  save with a toast and a Section Message.
- **A problem people have to fix stays.** Put it beside what failed, in a Section Message or a
  Field's message, not only in a toast that leaves after a few seconds. A toast can report background
  work that failed when nothing on the screen needs fixing. For a form's errors, see
  <DocLink to="Patterns/Forms and Validation" />.
- **Toast actions are shortcuts.** Anything a toast offers, such as Undo, has to be possible
  somewhere else too, because the toast goes away.
- **Ask in a dialog only when the answer is needed now.** Name the confirm button for what it does,
  such as "Delete matter", not "OK". A destructive action takes `tone="error"` on the dialog and on
  its confirm button.
- **Say what happened, then what to do.** The title says it in words, and the description or an
  action says what comes next. The icon and color repeat the tone; they never carry it alone.
- **Tone is meaning, not emphasis.** Use `error` only when something has gone wrong. A deadline
  that's coming is a `warning`.

</Section>

<Section title="Accessibility">

- Banner and Section Message are polite live regions (`role="status"`) by default, so a message
  that appears is read out without moving focus. Use `role="alert"` only for an urgent error that
  has to interrupt.
- Toast Group announces each toast through one polite live region. Moving focus into the stack
  pauses the timers, so keyboard users can reach a toast's actions before it goes.
- Inline Message isn't a live region, so a change to it isn't read out. When people need to hear
  the change as it happens, report it with a toast too.
- Field's message is the control's description (`aria-describedby`), and `state="error"` sets
  `aria-invalid` on the control.
- Modal Dialog moves focus inside when it opens, keeps it there, and returns it to where it was when
  it closes. Escape closes it.
- Status icons are decorative. Banner, Section Message, Inline Message, and Toast read the tone's
  name before the message (`statusLabel`), so the title doesn't repeat the tone, but it still has to
  say what happened.

</Section>
